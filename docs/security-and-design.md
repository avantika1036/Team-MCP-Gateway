# Security Model, Threats, and Design Trade-offs

This document records the current trust boundaries and limitations of the take-home implementation. It is not a claim that the platform is production-hardened.

## Assets

- User API keys and role/active-key records.
- The bootstrap administrator token and provisioner internal token (the chart currently uses the same Secret key for both purposes).
- Groq/LLM provider credential.
- Per-store WordPress administrator passwords, WooCommerce consumer keys/secrets, database passwords, and generic upstream credentials kept in Kubernetes Secrets.
- Product/order data and audit history.
- Kubernetes namespace, workload, RBAC, persistent-volume, and network-policy resources.

## Trust boundaries

1. **Browser to gateway:** browser requests carry a Urumi API key. The UI should never receive the LLM provider key or WooCommerce upstream credentials.
2. **MCP client to gateway:** `/mcp` requires a valid, active database-backed user API key. Calls are attributed to the authenticated user/key for audit.
3. **Gateway to upstream:** the gateway forwards tool calls only to registered, enabled upstreams. Upstream URLs are validated against configured hostname allow-lists; a slow/unreachable upstream is isolated from discovery/calls to other upstreams.
4. **Gateway to provisioner:** the provisioner is a ClusterIP-only service and its `/stores` and `/upstream-credentials` routes require an internal bearer token. Store creation/deletion and generic upstream credential management are exposed only through admin-authenticated gateway APIs.
5. **Provisioner to Kubernetes:** a dedicated ServiceAccount and scoped RBAC permit the provisioner to create/delete store namespaces and apply store-scoped resources. This is a high-impact control-plane permission and must be reviewed before production use.
6. **Store to store:** each provisioned store has a namespace, database and WordPress workload, credentials, PVCs, quota/LimitRange and network policies. The intent is to prevent direct cross-namespace network access.

## Design trade-offs

- **File-backed upstream registry:** simple, inspectable and persistent through a PVC; avoids adding a registry table/migration during the take-home. It is less suitable for multiple gateway replicas and concurrent writers.
- **Synchronous store provisioning:** easy to demonstrate and return a definitive `ready`/error result. Requests can take several minutes and HTTP failures complicate client retries. A production version should use an idempotent job queue with operation IDs, leases, and progress reporting.
- **One gateway/provisioner replica:** reduces coordination complexity for a local demo. Horizontal scaling would require shared registry semantics and distributed provisioning locks.
- **Streamable HTTP MCP transport:** one HTTP endpoint supports local UI and external MCP clients. API-key authentication is gateway-specific; external clients must send a supported `Authorization: Bearer` header.
- **Per-store Kubernetes namespace:** provides a stronger separation boundary than only logical tenant IDs and enables independent resource quotas. It increases resource overhead and requires careful namespace/RBAC lifecycle code.
- **Groq Responses API:** the chat agent uses function calling and keeps tool execution behind the authenticated MCP gateway. The implementation is provider-shape-specific; provider compatibility must be tested rather than inferred from a similar base URL.

## Production hardening not included in this MVP

HTTPS/TLS and managed secrets, backups and restore tests, API rate limits, structured metrics/tracing, secret rotation, user-level tool scopes, formal threat testing, admission-policy portability checks, and resilient asynchronous provisioning are not fully implemented. Do not treat a successful local demo as a production security certification.
